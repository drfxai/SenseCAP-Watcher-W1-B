# SenseCAP Watcher W1-B — بازیابی فریمور اصلی کارخانه

[وب‌فلشر](https://drfxai.github.io/SenseCAP-Watcher-W1-B/) · [دانلود بسته کامل](https://drfxai.github.io/SenseCAP-Watcher-W1-B/downloads/watcher-factory-1.1.7.zip)

بسته **کلاسیک کارخانه Seeed نسخه 1.1.7** برای سخت‌افزار Watcher با ESP32-S3 و فلش 32 MB. این فریمور Maximus OS یا Watcher Agent / Xiaozhi نیست. باینری‌های اصلی بدون تغییر از [مخزن رسمی Seeed](https://github.com/Seeed-Studio/OSHW-SenseCAP-Watcher/tree/3ca69aefa8441f57d38993a39df714048633d032/Firmware) گرفته شده‌اند. نسخه‌ای که دستگاه شما در روز خرید داشته ممکن است متفاوت باشد. این پروژه ابزار بازیابی مستقل است. فایل مشخصات دستگاه مالک، شامل EUI، سریال و KEY چاپی، بنا به درخواست صریح مالک در مخزن قرار گرفته است؛ این فایل تصویر پارتیشن کارخانه نیست.

## نکته تعیین‌کننده برای دستگاه کاملاً پاک‌شده

**نصب فریمور، اطلاعات کارخانه حذف‌شده را تولید نمی‌کند.** پارتیشن `nvsfactory` در آدرس `0x9000` با طول `0x32000` شامل اطلاعات اختصاصی اتصال به SenseCraft است. EUI و شماره‌سریال به‌تنهایی جای آن را نمی‌گیرند. عکس جعبه و EUI برای درخواست کمک از [پشتیبانی Seeed](https://www.seeedstudio.com/contacts) مفیدند؛ امکان بازیابی را باید خود سازنده تأیید کند.

بکاپی که بعد از پاک‌شدن می‌گیرید فقط وضعیت فعلی را ذخیره می‌کند. فایل `nvsfactory.bin` دستگاه دیگری را استفاده نکنید. واردکردن EUI در اپلیکیشن، جای بازنویسی اعتبارنامه‌های کارخانه در فلش را نمی‌گیرد. `factory_info` در فریمور اصلی فرمان نمایش اطلاعات است، نه ساختن هویت.

## چرا KEY روی برچسب برای بازسازی کامل کافی نیست؟

کد رسمی نسخه 1.1.7، اطلاعات کارخانه را از namespace به نام `device_info` می‌خواند و `CODE_SK`، `DEV_KEY_SK` و `AI_KEY_SK` را جداگانه نگهداری می‌کند. KEY چاپ‌شده ۱۶ کاراکتری را نباید بدون تأیید سازنده معادل `DEV_KEY_SK` فرض کرد: تابع اتصال ابری صراحتاً برای device key طول **۳۲ کاراکتر** را الزامی می‌داند. کلید AI هم از فیلد جداگانه خوانده می‌شود. عکس برچسب و صفحه اپلیکیشن می‌تواند EUI، S/N و KEY چاپی را تأیید کند؛ این تصاویر جای دامپ پارتیشن یا کلیدهای حذف‌شده را نمی‌گیرند.

شواهد در کد رسمی همان نسخه:

- [خواندن فیلدهای جداگانه کارخانه](https://github.com/Seeed-Studio/SenseCAP-Watcher-Firmware/blob/95c23160936d9987bbdcc05ffff8dd62b679c5f3/examples/factory_firmware/main/util/factory_info.c)
- [الزام کلید ۳۲ کاراکتری در اتصال SenseCraft](https://github.com/Seeed-Studio/SenseCAP-Watcher-Firmware/blob/95c23160936d9987bbdcc05ffff8dd62b679c5f3/examples/factory_firmware/main/app/app_sensecraft.c#L901-L920)

فایل `public/device-profile.json` شامل اطلاعات خوانده‌شده از تصاویر مالک است؛ KEY چاپی نیز با اجازه صریح مالک در آن ثبت شده است. تا زمانی که مخزن و Pages عمومی‌اند، این فایل قابل دریافت است. این پروژه هیچ کلید ۳۲ کاراکتری را از روی EUI حدس نمی‌زند و پارتیشن هویت ناقص تولید نمی‌کند.

## رابط ساده وب‌فلشر

نمای اصلی فقط «بکاپ دستگاه» و «نصب دو مرحله‌ای» دارد. بکاپ با یک کلیک شامل اتصال، خواندن، دانلود و آزادسازی پورت است. نصب، پنجره‌ای با دو مرحله دارد و قبل از نوشتن ESP32 خودکار بکاپ می‌گیرد. در مرحله دوم، دریافت اسکریپت PowerShell به‌تنهایی موفقیت نصب محسوب نمی‌شود؛ ثبت پایان نصب صرفاً با تأیید صریح کاربر و برچسب `user-confirmed-native` در گزارش ذخیره می‌شود. روش مستقیم مرورگر نیز زیر ابزارهای پیشرفته باقی مانده است.

## نصب دو مرحله‌ای در وب‌فلشر

مرورگر Chrome یا Edge دسکتاپ با Web Serial، HTTPS یا localhost لازم است. کابل USB-C دیتا را به پورت پایین/کنار دستگاه وصل کنید؛ پورت پشت فقط برق است. برنامه‌های دیگر پورت سریال را ببندید.

### مرحله ۱ — ESP32-S3

1. در صفحه اصلی «نصب دو مرحله‌ای» را بزنید، جایگزینی برنامه و تنظیمات را تأیید و مرحله اول را شروع کنید. پورت ESP32 (روی سیستم مالک COM6) را انتخاب کنید.
2. ابزار خودکار بکاپ را ذخیره می‌کند، فایل‌های اصلی را با SHA-256 بررسی و نوشته‌ها را با MD5 تأیید می‌کند.
3. فقط محدوده‌های مشخص نوشته می‌شوند و حفظ `nvsfactory` بررسی می‌شود. تنظیمات NVS معمولی در نصب مرورگری بازنشانی می‌شوند. برای حفظ آن‌ها از اسکریپت CLI با `--keep-settings` استفاده کنید.

### مرحله ۲ — Himax با روش موفق گزارش‌شده روی ویندوز

روی سیستم مالک این دستگاه، **COM6 مربوط به ESP32-S3 و COM7 مربوط به Himax** است. مالک دستور رسمی `python-sscma==0.5.7` را با سرعت `921600` روی COM7 اجرا کرد؛ خروجی به `100%` رسید (حدود ۱۳ ثانیه) و خطایی نمایش نداد. [ثبت نتیجه مشاهده‌شده](../public/validation/himax-native-result.json). این شاهد اتمام انتقال از خروجی ترمینال است؛ بازخوانی کامل فلش، عملکرد دوربین بعد از بوت و بازیابی اعتبارنامه‌های SenseCraft هنوز از این خروجی قابل اثبات نیستند.

**اگر همین نصب را کامل کرده‌اید، تکرارش نکنید.** دستگاه را خاموش و روشن و عملکرد دوربین را بررسی کنید. نیازی به فلش دوباره ESP32 نیست.

[دانلود نصب‌کننده PowerShell مخصوص COM7](https://drfxai.github.io/SenseCAP-Watcher-W1-B/downloads/flash-himax-com7.ps1) · [کد اسکریپت](../tools/flash-himax.ps1)

تب وب‌فلشر و برنامه‌های سریال را ببندید. PowerShell را در پوشه فایل دانلودشده باز و اجرا کنید:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\flash-himax-com7.ps1
```

ExecutionPolicy فقط برای همان فرایند تغییر می‌کند. اسکریپت وجود پورت را بررسی می‌کند، استفاده از COM6 را برای این دستگاه رد می‌کند، بسته رسمی نسخه 0.5.7 را نصب، فایل اصلی را دانلود و اندازه و SHA-256 را بررسی می‌کند. سپس همان دستور آزمایش‌شده مالک را اجرا می‌کند:

```powershell
py -m sscma.cli.cli flasher -p COM7 -b 921600 -f "$env:TEMP\watcher-himax-recovery\himax_factory.img"
```

وقتی ابزار منتظر بوت‌لودر است، دکمه ریست سخت‌افزاری دستگاه را بزنید. خروجی باید ۱۰۰٪ و بدون `Error` یا `Traceback` باشد. ابزار upstream بعضی خطاها را با exit code صفر خاتمه می‌دهد؛ اسکریپت به‌تنهایی از روی exit code موفقیت اعلام نمی‌کند. اسکریپت توسط این پروژه روی ویندوز اجرا نشده است؛ دستور اصلی بالا طبق خروجی ارسالی مالک روی دستگاه واقعی تا پایان انتقال اجرا شده است.

شماره COM روی سیستم دیگر ممکن است متفاوت باشد. پارامتر `-Port` در اسکریپت برای پورت دیگری قابل استفاده است؛ COM6 طبق نگاشت همین دستگاه محافظت می‌شود. اسکریپت در ZIP نیز با مسیر `tools/flash-himax.ps1` قرار دارد.

### گزینه پیشرفته مرحله ۲ — نصب مستقیم Himax در مرورگر (آزمایشی)

این گزینه داخل پنجره نصب و بخش «ابزارهای پیشرفته» قرار دارد. مسیر پیش‌فرض مرحله دوم، ابزار رسمی PowerShell است.

1. پس از موفقیت مرحله اول، بخش «ابزارهای پیشرفته» را باز کنید و «نصب مرورگری Himax (آزمایشی)» را بزنید. مرحله دوم پس از مرحله اول فعال می‌شود. اگر صفحه دوباره باز شده یا مرحله اول قبلاً نصب شده است، فایل گزارش موفق همان دستگاه را در «ادامه از گزارش نصب قبلی» وارد کنید؛ نیازی به نوشتن دوباره ESP32 نیست. گزارش فقط سابقه نصب را نشان می‌دهد و تأیید زنده اتصال به همان دستگاه نیست.
2. اگر دقیقاً یک پورت سازگار دیگر از قبل اجازه دسترسی داشته باشد، ابزار آن را انتخاب می‌کند؛ در غیر این صورت پنجره انتخاب پورت باز می‌شود. پورت دیگر Watcher را انتخاب کنید. مرورگر اجازه انتخاب بی‌صدا برای پورت‌های جدید نمی‌دهد. حروف A/B یا شماره پورت‌ها مبنای حدس نیستند.
3. فایل رسمی Himax دانلود و با SHA-256 ثابت بررسی می‌شود. اتصال UART با سرعت `921600` برقرار می‌شود. فرمان رسمی `AT+RST` برای راه‌اندازی مجدد امتحان می‌شود؛ اگر پاسخ نیامد، هنگام انتظار، دکمه ریست سخت‌افزاری دستگاه را بزنید و کابل را جدا نکنید. برای تراشه کاملاً پاک‌شده نیز بوت‌لودر باید قابل دسترسی باشد.
4. **بدون متن شناخته‌شده بوت‌لودر Himax، پیام انتقال XMODEM و دو درخواست مستقل آمادگی CRC، هیچ بسته فریموری ارسال نمی‌شود.** انتخاب مجدد همان پورت ESP32 پیش از انتقال رد می‌شود. پورت/تراشه نامناسب یا نبود پاسخ، عملیات را با خطا متوقف می‌کند.
5. فایل با XMODEM-CRC، بسته‌های ۱۲۸ بایتی، شمارنده، ACK و تلاش مجدد ارسال می‌شود. برای اولین بسته، حداکثر ۶۰ ثانیه برای پاسخ گیرنده مطابق ابزار Python رسمی فرصت داده می‌شود. فقط پس از تأیید پایان انتقال و دریافت پیام پایان عملیات بوت‌لودر، فرمان راه‌اندازی مجدد فرستاده و مرحله دوم موفق اعلام می‌شود.

تأیید Himax بر مبنای CRC انتقال، ACK بسته‌ها و پیام پایان بوت‌لودر است؛ **بازخوانی کامل فلش و مقایسه SHA-256 از تراشه انجام نمی‌شود**. شناسایی از روی بوت‌لودر است و EUI برد در مرحله Himax قابل اثبات نیست؛ هر دو پورت باید متعلق به همان Watcher باشند. قطع کابل یا لغو هنگام نوشتن ممکن است نیازمند اجرای دوباره مرحله Himax باشد. روش مرورگری روی دستگاه مالک به نبود پاسخ بوت‌لودر یا تأییدنشدن بسته اول برخورد کرده و موفقیت آن تأیید نشده است؛ پروتکل و رابط با گیرنده شبیه‌سازی‌شده آزموده شده‌اند. روش PowerShell بالا طبق خروجی مالک به پایان انتقال رسیده است.

بعد از موفقیت مرحله اول، از بخش «راهنما، فایل‌ها و گزارش»، «دانلود گزارش نصب» فایل JSON شامل مشخصات دستگاه، مراحل موفق، تلاش ناموفق Himax، خطای دقیق، آخرین وضعیت پورت/بوت‌لودر، تعداد بایت تأییدشده و لاگ عملیات را می‌سازد. برای تغییر پورت، «پورت Himax را دستی انتخاب می‌کنم» را فعال کنید؛ پس از خطا این گزینه خودکار فعال می‌شود. این گزارش اثبات بازگردانی اعتبارنامه‌های SenseCraft نیست. فایل مشخصات مرجع در [device-profile.json](../public/device-profile.json) است؛ **شماره‌سریال و EUI داخل باینری‌های اصلی Seeed تغییر داده نشده‌اند** و پارتیشن کارخانه پاک‌شده صرفاً از روی برچسب بازسازی نمی‌شود.

هیچ فرمان `erase_flash` صادر نمی‌شود. فایل یکپارچه BIN با فاصله‌های پرشده ارائه نمی‌کنیم چون نوشتن آن از آدرس صفر می‌تواند اطلاعات هویتی موجود را پاک کند. ZIP شامل فایل‌های جداگانه و آدرس‌های صحیح است. داده خارج از محدوده‌های نوشته‌شده لزوماً پاک نمی‌شود. عملیات سریال و بکاپ در مرورگر انجام می‌شود؛ بکاپ به سرور ارسال نمی‌شود.

## خط فرمان — ویندوز، لینوکس، macOS

ZIP را استخراج کنید و از پوشه اصلی آن اجرا کنید (یا مخزن را clone کنید). Python 3.10+ لازم است. `COM5` را با پورت واقعی ESP32 جایگزین کنید؛ روی لینوکس مثلاً `/dev/ttyACM0` و روی مک `/dev/cu.…` است.

```sh
python -m pip install -r requirements.txt
python tools/verify_firmware.py
python tools/flash.py --port COM5
```

اسکریپت ابتدا بکاپ خصوصی را در `watcher-backups/` ذخیره می‌کند؛ سپس فایل‌ها را جداگانه می‌نویسد و حفظ پارتیشن کارخانه را بررسی می‌کند. برای نگه‌داشتن NVS معمولی، `--keep-settings` اضافه کنید. اگر ارتباط ناپایدار بود `--baud 115200` را امتحان کنید. این ابزار فقط برای Watcher با فلش 32 MB است؛ پیش از اجرای CLI با `python -m esptool --chip esp32s3 --port COM5 flash_id` سخت‌افزار را بررسی کنید.

### بازگرداندن بکاپ واقعی همان دستگاه

فقط اگر بکاپ **پیش از پاک‌کردن** یا فایل معتبر مخصوص دستگاه از سازنده دارید، بعد از نصب بسته اصلی اجرا کنید. نام و پورت نمونه را عوض کنید. محدوده و طول زیر برای همین جدول پارتیشن است؛ فایل نمونه را از اینترنت جایگزین نکنید.

```sh
python -m esptool --chip esp32s3 --port COM5 write_flash 0x9000 YOUR_OWN_nvsfactory.bin
python -m esptool --chip esp32s3 --port COM5 verify_flash 0x9000 YOUR_OWN_nvsfactory.bin
```

بکاپ این پروژه دقیقاً `204800` بایت است. هر فایل با طول یا قالب متفاوت را پیش از نوشتن با پشتیبانی سازنده بررسی کنید. این دستور سریال دلخواه یا EUI جدید تولید نمی‌کند.

`a278e722ffecb09fe8251b1ac2d0b8ec1d803fb0e5041116c6d093729a6b97f5`

در این فایل namespace کارخانه `device_info` و فیلدهای `SN_SK` و `EUI_SK` وجود نداشتند؛ دو صفحه NVS معتبر و بخش‌هایی از داده‌های قدیمی با ساختار دیگر دیده شد. اصلاح با مولد رسمی Espressif ESP-IDF v5.2.1 ساخته شده و ورودی‌های افزوده‌شده و CRC آن‌ها با parser مستقل همان نسخه بررسی شده‌اند. فقط ۱۹ خانه قبلاً خالی و bitmap متناظر در صفحه فعال استفاده می‌شود؛ تمام ۳۸ رکورد موجود و بایت‌های دیگر، از جمله داده‌های قدیمی غیر NVS، دست‌نخورده می‌مانند. این به معنی سالم‌بودن همه بخش‌های قدیمی فایل نیست.

مقدارهای `SN_SK=113991275244700165` و `EUI_SK=2CF7F1C9647000A4` افزوده می‌شوند. `CODE_SK` از KEY چاپی روی برچسب گرفته می‌شود، چون کد نمایش EUI به این فیلد هم نیاز دارد. شش فیلد ناموجود دیگر (`DEV_KEY_SK`، `AI_KEY_SK`، `ACCESS_KEY_SK`، `DEV_CTL_KEY_SK`، `BATCHID_SK` و `PLATFORM_SK`) به‌صورت رشته خالی ثبت می‌شوند تا loader فریمور، حافظه مقداردهی‌نشده را به‌جای اطلاعات گمشده نخواند. **هیچ کلید ابری حدس زده یا بازیابی نشده است.** این اصلاح فقط شناسه‌های معلوم را بازمی‌گرداند و روی سخت‌افزار هنوز آزموده نشده است.

فایل ورودی و خروجی شامل داده خصوصی NVS است؛ باینری کامل در مخزن منتشر نشده است. اسکریپت فقط patch مربوط به فیلدهای معلوم را دارد، فایل اصلی را تغییر نمی‌دهد و روی سیستم مالک همان باینری بررسی‌شده را می‌سازد. اگر ورودی متفاوت باشد، اجرا را رد می‌کند.

در پوشه فایل اسکریپت و بکاپ، اجرا کنید:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\repair-device-identity.ps1 -InputFile .\nvsfactory-2026-11-06T16-46-39-333Z.bin
```

فایل خروجی: `nvsfactory-W1-B-identity-fixed.bin` با SHA-256:

`18dff19b2bcdb1a7501db115f52ec9f841bf6e9da3c3fc0a98280d8bb3813fe7`

فقط برای جدول پارتیشن رسمی این پروژه و پورت **COM6 دستگاه مالک**، پس از بستن تب وب‌فلشر و برنامه‌های سریال:

```powershell
py -m pip install esptool==4.8.1
py -m esptool --chip esp32s3 --port COM6 --baud 460800 write_flash 0x9000 .\nvsfactory-W1-B-identity-fixed.bin
py -m esptool --chip esp32s3 --port COM6 --baud 460800 verify_flash 0x9000 .\nvsfactory-W1-B-identity-fixed.bin
```

این فایل را روی COM7 یا در آدرس صفر ننویسید. بکاپ اصلی را نگه دارید؛ در صورت نیاز با همان دستور و آدرس `0x9000` قابل بازگرداندن است. بعد از نوشتن و تأیید، دستگاه را خاموش و روشن و S/N و EUI را در تنظیمات بررسی کنید. موفقیت این اصلاح هنوز روی دستگاه واقعی تأیید نشده است.


برای ساخت ZIP قابل دانلود: `python tools/package_firmware.py` و سپس `npm run build`. برای آزمون مرورگر: `npx playwright install chromium && npm run test:browser`.
